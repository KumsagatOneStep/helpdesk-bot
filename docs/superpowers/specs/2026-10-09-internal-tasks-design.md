# Helpdesk-бот: внутренние задачи специалистов — дизайн

Дата: 2026-10-09. Статус: на ревью.

Это первая из трёх частей доработки. Вторая — голосовой ввод при создании задачи (распознавание речи в текст), третья — склад ноутбуков (координатор ведёт наличие, специалист спрашивает бота). Они проектируются отдельно, после этой.

## 1. Цель

Специалисты сами создают задачи в боте: чтобы не забыть и чтобы поделиться с коллегами. Задачи — отдельная сущность, не связанная с WhatsApp: у них нет клиента, ответы никогда не уходят в WhatsApp.

В команде три человека: два helpdesk-специалиста и координатор. Координатор делает и helpdesk-работу, и свою; helpdesk-специалисты — только helpdesk.

**Критерии успеха**
- Любой специалист за несколько нажатий создаёт задачу с типом, описанием, «для кого» и сроком.
- Задача типа «Координатор», созданная helpdesk-специалистом, приходит координатору, создатель узнаёт, что тот принял.
- Исполнитель может попросить помощи — задачу забирает другой; одна задача никогда не достаётся двоим.
- Участники обсуждают задачу ответами на её карточку; обсуждение хранится в истории задачи.
- В день срока и при просрочке бот напоминает; после перезапуска напоминания не дублируются.
- Задачи видны в «Мои заявки», поиске, `/stats` и выгрузке xlsx.

**Решения пользователя**
| Вопрос | Решение |
|---|---|
| Заявки из WhatsApp | Без изменений: общие, типа у них нет |
| Тип задачи | Выбирает создатель (любой, включая координатора): Helpdesk или Координатор |
| После создания | Закреплена за создателем, если он может её выполнять; иначе уходит тем, кто может |
| Не успеваю | Кнопка «🆘 Нужна помощь» — задача уходит другим с «Взять» |
| Обсуждение | Комментарии внутри задачи (reply на карточку), без общей группы |
| Поля | Тип, описание (+ фото/файл), для кого (необяз.), срок (необяз.) |
| Срок | Дата без времени; напоминание утром в день срока, затем каждое утро при просрочке |
| Реализация | Отдельный модуль `tasks/` и свои таблицы, код заявок не трогаем |

**Вне рамок:** голосовой ввод (часть 2), склад (часть 3), срок с точным временем, повторяющиеся задачи, подзадачи, редактирование задачи после создания, переоткрытие закрытой задачи, смена типа после создания.

## 2. Роли и правила доставки

**Роль специалиста.** Новое поле `staff.role`: `helpdesk` (по умолчанию) или `coordinator`. Меняет админ в `/staff` кнопкой «Роль: Helpdesk ↔ Координатор». Признак `is_admin` не меняется и от роли не зависит. Координаторов может быть несколько — правила ниже написаны для «координаторов» во множественном числе.

**Кто может выполнять** (eligible) — активные (`status='active'`) специалисты:
- задача `helpdesk` — все;
- задача `coordinator` — только с ролью `coordinator`.

**Участники задачи** — все, кто может её выполнять, плюс создатель. Состав фиксируется при создании (таблица `task_cards`); специалист, одобренный позже, старые задачи не получает. Участникам приходят комментарии и сообщение о закрытии.

**При создании:**
| Создатель | Тип | Итог |
|---|---|---|
| может выполнять | любой | `in_progress`, исполнитель — создатель; остальные участники получают карточку без кнопок |
| не может (helpdesk → Координатор) | coordinator | `queued`; координаторам (независимо от смены) приходит карточка с [Принять]; создателю — карточка без кнопок |

Если создатель не может выполнять задачу, а активных координаторов нет, задача не создаётся: «Координатор не назначен. Обратитесь к админу (/staff)».

После «Принять» создателю приходит «✅ <имя> принял(а) З-12», у остальных координаторов кнопка пропадает.

**Нумерация.** `З-<id>` (кириллическая «З»). `/open` и поиск понимают `З-12`, `з12`, `З 12`.

## 3. Сценарии

### 3.1 Создание

В меню (`telegram/menu.py`) — кнопка «➕ Новая задача». Пошаговый диалог (aiogram FSM), на каждом шаге кнопка «Отмена»:

1. **Тип:** [Helpdesk] [Координатор].
2. **Описание:** текст; либо фото/документ — подпись становится описанием, файл сохраняется как вложение. Фото без подписи — бот просит прислать текст описания, файл запоминается. Пустое описание не принимается. Максимум 2000 символов.
3. **Для кого:** свободный текст до 200 символов или [Пропустить].
4. **Срок:** [Сегодня] [Завтра] [Через неделю] [Своя дата] [Без срока]. «Своя дата» — ввод `ДД.ММ` или `ДД.ММ.ГГГГ`; без года — ближайшая будущая такая дата; дата в прошлом отклоняется с просьбой ввести заново.
5. **Сводка** с [Создать] [Отмена].

Нажатие кнопки устаревшего шага (после отмены или завершения) отвечает «Диалог уже завершён». Команды меню во время диалога завершают его, как сейчас поиск.

### 3.2 Карточка

```
📌 З-12 · Helpdesk · срок 10.10
Для: Иванова, каб. 214
Заменить картридж в принтере HP
Создал: Ерлан · Исполнитель: Ерлан
```
Тип «Координатор» помечается `🧭`. Без срока — строка срока не выводится. Нет исполнителя — «Исполнитель: —». Вложение отправляется вместе с карточкой (фото/документ с подписью-карточкой).

Кнопки зависят от получателя:
- исполнитель: [✅ Закрыть] [🆘 Нужна помощь] (вторая — только если есть другой, кто может выполнять);
- создатель, не являющийся исполнителем: [✅ Закрыть];
- в очереди, получатель может выполнять: [Взять] (или [Принять] при первичной отправке координатору);
- остальным — без кнопок.

Админ закрывает чужие задачи через `/open З-12` (в его карточке есть [✅ Закрыть]).

### 3.3 «🆘 Нужна помощь»

Только исполнитель. Задача → `queued`, исполнитель снимается. Карточку с [Взять] получают все, кто может её выполнять **и на смене**, кроме бывшего исполнителя. Первый нажавший становится исполнителем (блокировка строки `SELECT … FOR UPDATE`), у остальных кнопка снимается, второму нажавшему — «Уже взял(а) <имя>». Бывшему исполнителю и создателю — «🤝 З-12 взял(а) <имя>».

Если на смене никого, кроме исполнителя: задача остаётся на нём, ответ «Сейчас никого на смене — задача осталась за вами».

При `/on` специалист получает карточки всех `queued`-задач, которые может выполнять (как `deliver_queue_to` для заявок).

### 3.4 Комментарии

Reply на любую карточку или сообщение задачи (их связь хранится в `task_links`) — комментарий. Текст, фото, документ, голосовое пересылаются всем остальным участникам: «💬 З-12 · Ерлан: …». Пересланное сообщение тоже связывается с задачей, поэтому отвечать можно на него. Комментарий сохраняется в `task_messages`. Комментировать закрытую задачу нельзя: «З-12 уже закрыта».

Важно: обработка reply сначала проверяет `task_links`, и только если связи нет — переходит к существующей логике ответа клиенту WhatsApp. Сообщение, связанное с задачей, никогда не попадает в WhatsApp.

### 3.5 Закрытие

Исполнитель, создатель или админ: [✅ Закрыть] → `closed`, `closed_at`, `closed_by_id`. Кнопки снимаются у всех, участникам — «✅ З-12 закрыта (<имя>)». Повторное нажатие — «Уже закрыта».

### 3.6 Где видны задачи

- **«Мои заявки» (`/my`)** — после заявок блок «Мои задачи»: открытые, где я исполнитель, сортировка по сроку (без срока — в конце), просроченные с `⚠️`. Отдельно «Ждут исполнителя» — `queued`, которые я могу взять.
- **Поиск** — дополнительно ищет по `description` и `requester` (ILIKE), выводит задачи отдельным блоком.
- **`/open З-12`** — карточка с кнопками по правам + последние 5 комментариев. Доступна участникам и админу.

## 4. Сроки и напоминания

Часовой пояс — `settings.tz`. Новый параметр `.env` `TASK_REMIND_HOUR` (по умолчанию 9). Проверка раз в минуту в существующем цикле `reminders.run` (новая функция `tasks.reminders.run_once`).

Для открытых задач со сроком, если местное время ≥ `TASK_REMIND_HOUR:00` и `last_reminded_on` ≠ сегодня:
- `due_date == сегодня` — «⏰ Сегодня срок: З-12 …» исполнителю (нет исполнителя — создателю);
- `due_date < сегодня` — «⚠️ Просрочена З-12 (срок был 10.10)» исполнителю (или создателю) и всем координаторам, без дублей;
- затем `last_reminded_on = сегодня`.

Обработка с `FOR UPDATE SKIP LOCKED`, отправка через outbox в той же транзакции — перезапуск не даёт повторов в тот же день.

## 5. Модель данных

Новая миграция Alembic.

```
staff.role            varchar(16) not null default 'helpdesk'   -- helpdesk | coordinator

tasks
  id, kind varchar(16)            -- helpdesk | coordinator
  status varchar(16)              -- queued | in_progress | closed
  description text, requester varchar(200) null
  due_date date null, last_reminded_on date null
  file_path varchar(500) null, file_name varchar(255) null, file_kind varchar(16) null
  creator_id → staff, assignee_id → staff null, closed_by_id → staff null
  created_at, taken_at null, closed_at null
  index (status, due_date)

task_messages       -- комментарии
  id, task_id → tasks (index), staff_id → staff, kind, text null,
  file_path null, file_name null, created_at

task_events
  id, task_id → tasks (index), type varchar(32), staff_id → staff null, created_at
  -- created | accepted | taken | help | closed | reminded_due | reminded_overdue | delivery_failed

task_cards          -- как tg_cards
  id, task_id (index), staff_id, tg_chat_id, tg_message_id,
  buttons varchar(16)  -- none | work | owner | take | accept
  state varchar(16), sent_at

task_links          -- как tg_links
  (tg_chat_id, tg_message_id) PK, task_id
```

Файлы вложений и комментариев — в `files_dir/tasks/<task_id>/`, тем же кодом, что для заявок (`files.py`).

## 6. Модули

- `tasks/service.py` — создание, правила доставки, take/accept, help, close, comment, `my_tasks`, `queued_for`, поиск. Без aiogram.
- `tasks/render.py` — текст карточки и кнопки по получателю.
- `tasks/reminders.py` — `run_once(sf, now)`.
- `telegram/task_handlers.py` — FSM создания, callback-кнопки задач (`task:take:<id>`, `task:close:<id>`, `task:help:<id>`, `task:new:*`), отдельный router, подключается до общих обработчиков.
- `telegram/handlers.py` — правки: `/my`, поиск, `/open`, `/on`, роутинг reply (сначала задачи), кнопка роли в `/staff`.
- `staff/service.py` — смена роли, выбор eligible.
- `stats/service.py`, `stats/export.py` — блок и лист задач.

Код заявок (`tickets/`) не меняется. Общие кусочки отправки карточек выносятся только если это не меняет поведение заявок.

## 7. Статистика и выгрузка

`/stats` за период — блок «Задачи»: создано, закрыто, просрочено сейчас, закрыто с опозданием; по типам; по исполнителям (закрыто). Выгрузка xlsx — лист «Задачи»: номер, тип, статус, описание, для кого, создатель, исполнитель, срок, создана, закрыта, «с опозданием» (да/нет). Ячейки через существующий `_safe` (защита от формул).

## 8. Надёжность и безопасность

- Вся отправка — через outbox в одной транзакции с изменением задачи; `delivery_failed` пишется в `task_events`, исполнителю (или создателю) — «⚠️ Не доставлено в З-12».
- Гонки «Взять»/«Принять»/«Закрыть» — блокировка строки задачи.
- `callback_data` — только числовые id, проверка формата как в аудите (c6f1793).
- Права проверяются в сервисе, а не только наличием кнопки: закрыть — исполнитель/создатель/админ; help — исполнитель; take — eligible и задача `queued`; `/open` — участник или админ.
- Описание, «для кого», имена, комментарии — `html.escape` при выводе.
- Ограничение размера вложений — существующий лимит Telegram-загрузки.

## 9. Тестирование

TDD, реальная тестовая БД (`make test-db && make check`). Покрыть:
- правила доставки — все строки таблицы из раздела 2, включая «нет координатора»;
- take/accept: успешный, повторный, конкурентный (два сеанса), не-eligible;
- help: уходит только на смене и не бывшему исполнителю; никого на смене; кнопка скрыта, когда некому отдать;
- комментарии: пересылка всем, кроме автора; связь пересланных; закрытая задача; reply на задачу не создаёт outbox `wa`;
- закрытие: права, повтор, уведомления;
- разбор даты: `ДД.ММ`, `ДД.ММ.ГГГГ`, прошлое, мусор;
- напоминания: до часа — нет; в час — да; повторный прогон в тот же день — нет; просрочка — исполнителю и координаторам без дублей; без исполнителя — создателю;
- `/my`, поиск, `/open З-12` (разные написания), роль в `/staff`;
- статистика и лист xlsx;
- миграция вверх/вниз.

Существующие 155 тестов остаются зелёными.

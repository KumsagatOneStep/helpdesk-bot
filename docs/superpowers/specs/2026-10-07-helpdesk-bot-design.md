# Helpdesk-бот: WhatsApp → Telegram — дизайн v1

Дата: 2026-10-07. Статус: на ревью.

## 1. Цель

Внутренний IT-helpdesk. Сотрудники организации пишут на **один общий номер WhatsApp**. Бот превращает обращения в заявки и раздаёт их специалистам helpdesk (сейчас трое) в **Telegram**. Специалисты берут заявки, переписываются с пользователем через бота и закрывают их. Всё сохраняется: переписка, ход исполнения, статистика.

**Критерии успеха**
- Пользователь пишет в WhatsApp и в течение нескольких секунд получает номер заявки.
- Новая заявка появляется у всех специалистов на смене. После нажатия «Взять» у остальных она исчезает, и одна заявка никогда не достаётся двоим.
- Специалист отвечает в Telegram (текст, фото, файл, голосовое), и пользователь получает ответ в WhatsApp.
- Любую заявку можно найти и посмотреть её переписку и журнал событий. Есть статистика и выгрузка в Excel.
- После перезапуска бота или VPS сообщения не теряются.

**Решения пользователя (зафиксированы при обсуждении)**
| Вопрос | Решение |
|---|---|
| Связь с IT-платформой | Отдельный проект, своя база |
| Подключение WhatsApp | Green API, отдельный рабочий номер |
| Хостинг | VPS + Docker Compose |
| Интерфейс специалистов | Каждому в личный чат с ботом; после «Взять» у остальных карточка удаляется |
| Первое обращение | Бот спрашивает язык, ФИО, отдел/кабинет и запоминает по номеру |
| Статистика и архив | Только через команды в Telegram + Excel-выгрузка |
| Язык для пользователей | Русский и казахский на выбор; интерфейс специалистов на русском |
| Стек | Python 3.12, aiogram 3, PostgreSQL, Docker Compose |

**Вне рамок v1:** веб-панель, оценка работы пользователем, категории и авто-распределение, SLA, групповые чаты WhatsApp, рассылки пользователям, интеграция с IT-платформой.

## 2. Архитектура

```
 WhatsApp-пользователи                     Специалисты
        │                                        ▲ │
        ▼                                        │ ▼
   Green API  ◄── long polling ──┐   ┌── long polling ──► Telegram Bot API
                                 │   │
                    ┌────────────┴───┴────────────┐
                    │     helpdesk-bot (Python)    │
                    └──────────────┬───────────────┘
                                   ▼
                     PostgreSQL 16 + ежедневный pg_dump
```

- Один процесс на asyncio. Внутри параллельно работают четыре задачи: опрос Green API, опрос Telegram (aiogram), обработчик очереди отправки (outbox), таймер напоминаний.
- Оба канала работают через опрос. **Домен, SSL и входящие порты не нужны.**
- Docker Compose поднимает три сервиса: `bot`, `db` (postgres:16), `backup` (ежедневный `pg_dump`, хранение 14 дней). У всех `restart: unless-stopped`.
- Вложения хранятся в томе `/data/files/<год>/<месяц>/<uuid>.<ext>`.
- Часовой пояс задаётся в `.env` (`TZ=Asia/Almaty`). В базе время хранится в UTC, специалистам показывается в локальном.

### Модули (`src/helpdesk/`)

| Модуль | Ответственность | Зависит от |
|---|---|---|
| `config` | Чтение `.env` (pydantic-settings) | — |
| `db` | Модели SQLAlchemy 2 (async), сессии, миграции Alembic | config |
| `whatsapp` | Клиент Green API: получение/удаление уведомлений, отправка текста и файлов, скачивание вложений, разбор входящих в `IncomingMessage` | config |
| `intake` | Анкета нового пользователя, тексты RU/KZ | db, ports |
| `tickets` | Логика заявок: создать, добавить сообщение, взять, вернуть, закрыть, сменить активную; журнал событий | db, ports |
| `telegram` | Обработчики aiogram, клавиатуры, рендер карточек; вызывает `tickets`/`stats`, ничего не решает сам | tickets, stats, db |
| `delivery` | Outbox: надёжная отправка в WhatsApp и Telegram с повторами | whatsapp, db |
| `reminders` | Раз в минуту ищет заявки, которые никто не взял, и рассылает напоминания | tickets, db |
| `stats` | Расчёт статистики, поиск, выгрузка xlsx (openpyxl) | db |
| `main` | Сборка и запуск всех задач | всё |

`tickets` и `intake` не обращаются к Green API и aiogram напрямую. Они работают через порты (`Protocol`): `ClientNotifier` (отправить пользователю в WhatsApp) и `StaffNotifier` (отправить, удалить или отредактировать карточку у специалиста). В тестах вместо них подставляются фейки.

## 3. Модель данных

```
clients        id, wa_chat_id (уник., "77011234567@c.us"), phone, wa_name,
               full_name, location (отдел/кабинет), lang ('ru'|'kk'),
               intake_step ('lang'|'name'|'location'|'done'), created_at

staff          id, tg_user_id (уник.), tg_chat_id, name, is_admin,
               status ('pending'|'active'|'disabled'), on_shift (bool),
               active_ticket_id (nullable), created_at

tickets        id (номер заявки), client_id, status ('new'|'in_progress'|'closed'),
               assignee_id (nullable), created_at, first_taken_at, closed_at,
               closed_by_id, last_broadcast_at

messages       id, client_id, ticket_id (nullable — до создания заявки),
               direction ('in'|'out'), staff_id (для 'out'),
               kind ('text'|'image'|'document'|'audio'|'video'|'other'),
               text, file_path, file_name, wa_message_id, created_at

ticket_events  id, ticket_id, type ('created'|'taken'|'returned'|'closed'|
               'delivery_failed'), staff_id, created_at

tg_cards       id, ticket_id, staff_id, tg_chat_id, tg_message_id, sent_at,
               state ('open'|'deleted'|'marked')   -- карточки очереди с «Взять»

tg_links       tg_chat_id, tg_message_id, ticket_id   -- для маршрутизации «Ответить»

outbox         id, channel ('wa'|'tg'), payload (jsonb), attempts, next_attempt_at,
               status ('pending'|'sent'|'failed'), last_error, message_id (nullable)
```

Инвариант: у одного клиента не больше одной незакрытой заявки (частичный уникальный индекс `tickets(client_id) WHERE status <> 'closed'`).

## 4. Сценарии

### 4.1 Входящее сообщение WhatsApp

1. Поллер вызывает `receiveNotification` (таймаут 20 с). Обрабатываются только `incomingMessageReceived` из личных чатов (`@c.us`). Сообщения из групп и служебные уведомления подтверждаются (`deleteNotification`) и игнорируются.
2. Защита от дублей: если `wa_message_id` уже есть в `messages`, сообщение пропускается.
3. Вложение скачивается (`downloadUrl` из уведомления) и сохраняется на диск.
4. Дальше сообщение идёт в `intake` или в `tickets`. Уведомление подтверждается **только после** коммита транзакции: если бот упадёт посередине, Green API отдаст его снова (Green API хранит уведомления около 24 часов).

### 4.2 Анкета (intake)

- Новый номер: создаётся `clients` с `intake_step='lang'`, первое сообщение сохраняется в `messages` с `ticket_id = NULL`. Бот отправляет двуязычный вопрос «1 — Русский / 2 — Қазақша».
- `lang`: ответ «1» или «2» (а также «рус», «қаз», «kaz» и т.п.). На любой другой ответ вопрос повторяется.
- `name`: «Укажите ФИО». Принимается любая непустая строка (2–100 символов).
- `location`: «Укажите отдел и кабинет». Принимается любая непустая строка.
- `done`: создаётся заявка, к ней привязываются все сохранённые сообщения с `ticket_id = NULL`, кроме ответов на вопросы анкеты. Ответы анкеты помечаются и в заявку не попадают.
- Если первое сообщение было вложением или анкету прислали одним сообщением без проблемы, заявка всё равно создаётся. Специалист увидит то, что есть.
- Изменить ФИО или кабинет в v1 может только специалист: `/client <номер заявки> name|location <значение>`.

### 4.3 Создание заявки и рассылка

- Если у клиента нет открытой заявки, создаётся новая (`status='new'`) и событие `created`. Пользователю на его языке уходит: «Заявка #125 принята. Специалист скоро ответит».
- Если открытая есть, сообщение добавляется в неё:
  - `in_progress`: пересылается исполнителю с заголовком `#125 · ФИО`;
  - `new`: у всех открытых карточек этой заявки обновляется текст (добавляется последнее сообщение).
- Рассылка: каждому `staff` со `status='active'` и `on_shift=true` уходит карточка:
  ```
  🆕 Заявка #125 · 14:02
  👤 Айгерим Сериккызы · Бухгалтерия, каб. 214
  📞 +7 701 123 45 67
  «Не печатает принтер»  [+ вложения отдельными сообщениями]
  [✋ Взять]
  ```
  Каждая карточка записывается в `tg_cards`.
- На смене никого нет: карточки не отправляются, админу уходит «⚠️ Заявка #125, на смене никого». Когда специалист включает `/on`, он получает карточки всех заявок со `status='new'`.

### 4.4 «Взять»

- Атомарно: `UPDATE tickets SET status='in_progress', assignee_id=:me, first_taken_at=COALESCE(first_taken_at, now()) WHERE id=:id AND status='new' RETURNING id`.
  - 0 строк: всплывающее сообщение «Уже взял <имя>», а карточка нажавшего удаляется.
  - 1 строка: событие `taken`, заявка становится активной у взявшего (`active_ticket_id`).
- Остальные открытые карточки этой заявки удаляются (`deleteMessage`). Если удаление не удалось (прошло больше 48 часов или другая ошибка), карточка редактируется в «🔒 #125 взял Ерлан» и помечается `marked`.
- Карточка взявшего заменяется рабочей карточкой с полной историей сообщений заявки и кнопками **[✅ Закрыть] [↩️ Вернуть]**.
- Пользователю уходит: «Вашей заявкой #125 занимается Ерлан».

### 4.5 Переписка специалиста

Каждое сообщение бота, относящееся к заявке, записывается в `tg_links`. Входящее сообщение специалиста (текст, фото, документ, голосовое, видео) маршрутизируется так:
1. Если это «Ответить» на сообщение из `tg_links` и заявка `in_progress` у этого специалиста, сообщение идёт в эту заявку.
2. Иначе в `active_ticket_id`, если она `in_progress` у него.
3. Иначе ответ: «Нет активной заявки. /my — ваши заявки».

После успешной постановки в outbox специалист получает короткое подтверждение «→ #125 Айгерим ✓», а в `messages` пишется запись с `direction='out'`. Чужую или закрытую заявку выбрать нельзя.

`/my` выводит список заявок специалиста в работе с кнопками [Перейти к #N]. Нажатие делает заявку активной и показывает последние 5 сообщений.

### 4.6 Вернуть и закрыть

- **Вернуть**: `status='new'`, `assignee_id=NULL`, событие `returned`. Если заявка была активной у специалиста, `active_ticket_id` сбрасывается. Заявка заново рассылается всем на смене (включая вернувшего). Пользователю ничего не отправляется.
- **Закрыть**: `status='closed'`, `closed_at`, `closed_by_id`, событие `closed`, сброс `active_ticket_id`. Пользователю: «Заявка #125 выполнена. Если проблема осталась, напишите снова». Следующее сообщение от него создаёт новую заявку.
- Закрыть и вернуть может только исполнитель или админ (админ — через `/find` и кнопки в карточке).

### 4.7 Напоминания

Раз в минуту: заявки со `status='new'` и `last_broadcast_at < now() - REMIND_AFTER` (по умолчанию 10 минут) рассылаются заново. Старые карточки удаляются, новые отправляются с пометкой «⏰ ждёт 10 мин» (20, 30…), `last_broadcast_at` обновляется.

### 4.8 Специалисты и доступ

- `ADMIN_TG_IDS` в `.env`: при первом `/start` такие пользователи создаются как `active` и `is_admin`.
- Остальные после `/start` получают `pending`, а админам приходит запрос: «Ерлан (@erlan) просит доступ [Одобрить] [Отклонить]». Пока статус не `active`, человек не получает ни карточек, ни команд.
- `/staff` (админ): список специалистов с кнопками [Отключить] / [Включить] / [Сделать админом].
- `/off` и `/on`: смена. Если специалист отключён или ушёл со смены, его заявки в работе остаются за ним.
- Если специалиста отключили (`disabled`), его заявки `in_progress` автоматически возвращаются в очередь.

## 5. Статистика, поиск, выгрузка

| Команда | Кто | Что |
|---|---|---|
| `/stats` | все | Кнопки [Сегодня] [Неделя] [Месяц]. Показывает: создано, закрыто, в работе, в очереди; по специалистам — взял, закрыл, среднее время решения; среднее время реакции (`first_taken_at - created_at`) и решения (`closed_at - created_at`) по закрытым за период; топ-5 отделов (`location`) |

| `/export` | все | Кнопки [Этот месяц] [Прошлый месяц] [Всё время]; xlsx: №, создана, ФИО, отдел/кабинет, телефон, первое сообщение, исполнитель, статус, взята, закрыта, реакция (мин), решение (мин) |

## 6. Надёжность и ошибки

- **Outbox.** Вся исходящая отправка (в WhatsApp и в Telegram, кроме мгновенных ответов на нажатия кнопок) сначала пишется в `outbox` в той же транзакции, что и изменение данных. Воркер отправляет сообщения с повторами: 5 попыток с паузой 5 с, 30 с, 2 мин, 10 мин, 30 мин. Если все попытки неудачны, `status='failed'`, событие `delivery_failed`, а исполнителю (или админам, если исполнителя нет) уходит «⚠️ Не доставлено в #125: <текст>».
- **Порядок.** Сообщения одного чата отправляются в порядке создания: воркер не берёт следующее сообщение чата, пока не отправлено предыдущее.
- **Перезапуск.** Уведомления Green API подтверждаются после коммита, offset Telegram хранит aiogram/Telegram, outbox лежит в базе. Поэтому после рестарта бот продолжает с того же места.
- **Неподдерживаемые типы** (стикер, локация, контакт, опрос, звонок) сохраняются как `kind='other'` с текстом «[стикер]» и т.п. Пользователю на его языке уходит: «Принимаются текст, фото, файлы и голосовые». Если есть открытая заявка, сообщение попадает и в неё.
- **Большие файлы.** Telegram Bot API отдаёт ботам файлы до 20 МБ. Если файл больше, специалист получает «Файл слишком большой, отправьте ссылкой».
- **Логи:** structlog в stdout, смотреть через `docker compose logs -f bot`.
- **Бэкап:** сервис `backup` каждый день в 03:00 делает `pg_dump` в том `backups/`, хранит 14 последних. Файлы вложений бэкапятся вместе с томом `/data` средствами VPS (описать в README).

## 8. Тестирование

- pytest + pytest-asyncio, тесты на настоящей PostgreSQL (тестовая база в Docker), миграции применяются перед прогоном.
- Порты `ClientNotifier`/`StaffNotifier` и клиент Green API подменены фейками, которые записывают вызовы.
- Обязательные сценарии:
  - анкета (оба языка, неверный выбор языка, первое сообщение попадает в заявку);
  - создание заявки и добавление в открытую;
  - гонка двух «Взять» (параллельно, ровно один победитель);
  - удаление карточек и фолбэк на редактирование;
  - маршрутизация ответа (reply → активная → нет активной; чужая заявка);
  - вернуть, закрыть, новое сообщение после закрытия;
  - напоминания;
  - доступ (pending, disabled, возврат заявок отключённого);
  - outbox (повторы, failed, порядок);
  - дедупликация входящих;
  - статистика на фиксированных данных, выгрузка xlsx.
- Разбор уведомлений Green API тестируется на сохранённых примерах JSON для каждого типа сообщения.
- Ручная приёмка: тестовый инстанс Green API, реальный номер и три Telegram-аккаунта, чек-лист в README.

## 9. Развёртывание

1. VPS (Ubuntu, 1 vCPU / 1–2 ГБ RAM) с Docker.
2. `git clone`, `cp .env.example .env`, заполнить.
3. `docker compose up -d`: миграции применяются при старте бота.
4. Green API: создать инстанс, отсканировать QR с телефона рабочего номера, в настройках инстанса включить получение входящих уведомлений, а webhook URL оставить пустым (работаем через `receiveNotification`).
5. Telegram: создать бота в @BotFather. Админ пишет `/start`, затем специалисты пишут `/start`, и админ их одобряет.
